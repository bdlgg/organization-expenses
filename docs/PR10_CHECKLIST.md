# ПР10 — административная панель Django и работа с данными через ORM

Практическая работа адаптирована к теме индивидуального проекта
**«Система учёта расходов организации»**. Сущности `Room`, `User` и `Booking`
из примера Roomly не переносились. Используются модели проекта: `Expense`,
`Category`, `Department` и `Document`.

## 5. Индивидуальный сквозной проект

### 5.1. Общий порядок

- [x] Продолжен существующий проект ПР9 без создания отдельного Django-проекта.
- [x] Сохранены приложения, маршруты, шаблоны, консольная версия и исходные
  данные ПР7.
- [x] Расширены модели и миграции, пользовательские страницы и документация.

### 5.2. Административная панель

- [x] Проверено подключение `django.contrib.admin`, аутентификации, сессий,
  сообщений и маршрута `/admin/`.
- [x] Модели `Category`, `Department`, `Document`, `Expense` зарегистрированы
  по одному разу.
- [x] В `ModelAdmin` настроены столбцы, ссылки, поиск, фильтры, сортировка и
  количество строк на странице.
- [x] Справочники поддерживают быстрые правки названия/номера в списке.
- [x] Расходы поддерживают быстрые правки суммы и статуса.
- [x] Для расхода настроены `autocomplete_fields`, `date_hierarchy`,
  `list_select_related` и поиск по связанным моделям.
- [x] В карточках категорий, подразделений и документов добавлены
  `TabularInline` для просмотра связанных расходов.
- [x] Встроенные таблицы расходов доступны только для чтения; переход к расходу
  выполняется по ссылке изменения.
- [x] Поля `id`, `slug` и вычисляемый `is_large` в карточке расхода доступны
  только для чтения.
- [x] Добавлены массовые действия: отметить как оплаченные, отменить и вернуть
  в обработку.
- [x] Добавлены русские названия приложений, моделей и полей, а также `help_text`.
- [x] Реализация использует встроенную систему разрешений Django; проверка
  ограничений доступа возможна через группы и права `view/add/change/delete`.

### 5.3. Работа с данными через Django ORM

- [x] Используются `all()`, `filter()`, `exclude()`, `order_by()`,
  `get_object_or_404()`, `Q`, `F()`, `values()`, `annotate()` и `aggregate()`.
- [x] Добавлены предметные методы `ExpenseQuerySet`: `pending()`, `approved()`,
  `paid()`, `cancelled()`, `not_cancelled()`, `for_date()`, `for_period()` и
  `above_amount()`.
- [x] Список расходов фильтруется по категории, подразделению, сумме, статусу,
  датам и номеру документа.
- [x] Сохранены сортировка, пагинация и передача параметров фильтрации между
  страницами.
- [x] Карточка расхода получает объект через `get_object_or_404()`.
- [x] Для связей `ForeignKey` применяется `select_related()`; в запросах
  статистики используются аннотации и агрегаты.
- [x] Отменённые расходы не включаются в фактические суммы, но остаются в журнале
  и учитываются в количестве отменённых записей.
- [x] Для просмотра сформированного SQL используются `.query` и `.explain()`;
  для подсчёта реальных запросов — `CaptureQueriesContext`.

### 5.4. Дополнительные возможности Django

- [x] **Django Debug Toolbar:** добавлена в `requirements.txt`; при установленном
  пакете и `DEBUG=True` приложение, middleware и маршрут `__debug__/`
  подключаются автоматически. В режиме `DJANGO_DEBUG=False` панель не
  подключается.
- [x] **Оптимизация ORM:** подробная карточка расхода и список загружают
  справочники через `select_related()`; оптимизация проверяется сравнением
  реальных SQL-запросов в тесте.
- [x] **TextChoices и менеджер:** добавлены статусы `PENDING`, `APPROVED`,
  `PAID`, `CANCELLED` и методы менеджера для выборок по состоянию и датам.
- [x] **Миграция статусов:** старые записи получают `PENDING`, поскольку исходная
  база ПР7 не содержала сведений о статусе. Данные и идентификаторы не удаляются.
- [x] **GeneratedField:** `is_large` вычисляется базой данных при сумме от
  10 000 ₽; поле не редактируется вручную.
- [x] **SlugField:** русские названия справочников транслитерируются в адрес;
  существующие записи получают уникальный slug через миграцию данных, новые —
  автоматически при сохранении.
- [x] **get_absolute_url():** каноническая карточка открывается по slug; старые
  числовые URL перенаправляют на новый адрес.
- [x] **Context processor:** общий контекст передаёт название проекта и число
  записей; сведения отображаются в общей навигации.

### 6.4. Качество кода и автоматизированные тесты

Проверки выполняются из корня проекта:

```bash
python manage.py check
python manage.py makemigrations --check --dry-run
python manage.py showmigrations
pytest -v
flake8 . --extend-exclude=venv,.venv
```

- [x] Проверка Django не выявляет ошибок конфигурации.
- [x] `makemigrations --check --dry-run` не находит несохранённых изменений
  моделей.
- [x] Миграция ПР10 применена к SQLite; старые даты остались пустыми, поскольку
  исходный файл ПР7 не содержал даты операции.
- [x] Тесты проверяют модели, связи, CRUD, статусы, фильтры, slug, GeneratedField,
  контекстный процессор, Admin inline и оптимизацию запросов.
- [x] Повторный импорт данных из ПР7 сохраняет уже внесённые дату и статус ПР10.
- [x] Веб-представления не возвращены к прямым SQL-запросам.
- [x] В ZIP не включаются виртуальное окружение, локальные настройки IDE и кэш.

**Примечание по ручной проверке:** Django Debug Toolbar подключается после
установки зависимостей на локальном компьютере. Для визуального просмотра SQL
запустите сервер при `DJANGO_DEBUG=True` и откройте список, карточку и страницы
фильтрации. В среде подготовки архив проверяется Django Test Client; наличие
панели отладки зависит от установки её дополнительного пакета.
